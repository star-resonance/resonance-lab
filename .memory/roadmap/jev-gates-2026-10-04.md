## Design
- **Gate 1** (needs the judge server, so a script run on the PC, not a mandatory stage): `gate_pass.py` -> `outputs/gate/<judge id>.jsonl`, one row per message `{pid/hash, category, probabilities, confidence, flags}` + a header row with the
  judge tags (model, prompt hash). Low confidence -> a review bucket, never a guessed category. Describe every option (article: Julia-1 misrouted bare labels, got 0.99 once each option had a description). Regex baseline first
  (recruitment: `ID:`, 募集, ...); the judge must beat it on a hand-labelled stratified sample (~200 lines; the judge pre-labels, the maintainer corrects) to be worth a GPU pass. Cutoffs are per model (article).
- **Gate 2** (pure, data part, tested on every OS): a target table in config (category -> weight), a deficit/quota rule, a **seeded** selection over the whole categorized pool (NOT a streaming accept/reject: arrival order would decide
  the dataset). Unselected messages stay in the pool, never deleted. Output: the selected rows plus a Korean worklist ordered by category deficit. `manifest.py` records raw sha, gate file sha, seed, targets: the dataset is reproducible.
- **The category is metadata only.** The app sends instruction + line at runtime (`stream-contract.md`); a category must never enter the training prompt.
- **Targets are a design choice**, not the natural mix: recruitment posts are templated (memorisation risk), hard categories (game talk, slang) matter more than their frequency. Treat the table as a sweepable data parameter
  (notebook: compare a ratio-gated dataset with the current one). Changing the composition changes the model: a feature with its own eval, not a refactor.
- Align the taxonomy with the eval set's `category` field (`eval_metrics.py` already reports per category).
- **Superseded 2026-10-04 by [`dataset-categories-2026-10-04.md`](dataset-categories-2026-10-04.md)** (taxonomy with descriptions + first recommended weights; the list below was the first draft). Starting categories (to be cut down by the sample): greetings, guild recruitment, party/dungeon recruitment, trade, daily chat, game talk, questions/help, reactions and thanks, system/bot lines, noise, other.

## What the llama.cpp article says (https://huggingface.co/blog/ggml-org/decision-models-in-llamacpp, 2026-10-02; read, NOT run)
- `POST /v1/systemone` on llama-server (PR #29818; server docs hold the reference — to read before pinning test fixtures), System One format of TypeSafe's Jev. Start: `llama serve -hf ggml-org/Kev-4B-GGUF`, needs the latest llama.cpp.
- Request: `{"state": "...", "questions": {id: {"type": "choice"|"score"|"noul", "instructions": "...", "criteria": ...}}}`. `choice`: `criteria` = options (with descriptions); answer `{choice, probabilities, confidence}`.
  `noul`: yes/no, **no `criteria`**; answer `{"type":"noul","noul": P(yes)}`. `score`: 2-10 ordered levels; answer `{score (expected level), legend, probabilities, confidence}`. `usage.output_tokens` is 0 (no generation).
  (The 2026-10-03 handoff had `noul` with `criteria` and a bare number as the answer: both wrong against the article.)
- Kev-4B, lev, OpenJev read the state once for all questions of a request: batch the questions of one message. A `model` field picks a model in router mode; ignored with a single model.
- Models: Julia-1 144M (mmBERT, 50+ languages, Apache 2.0, 3 ms), Laya 421M (English), Kev-4B (Qwen3.5-4B-Base, English, Apache 2.0), lev 4B (English), OpenJev 27B (en/de/fr/hi/zh/ja, images, **CC BY-NC 4.0**, ~16 GB at Q4: does not fit with a translator).
  Julia-1 and OpenJev list Japanese; the 4B models list English only (probe on our data decides). Korean is listed for none.

## Gate 2 plan (maintainer's answers, 2026-10-04) — design only, nothing built
Decisions: batch run over a big raw log (not live); "set aside" = just a category, no review queue; **recipe uses `weight` (relative sizes; a category's share = weight / total weight, so no need to add up to 1; changed from `share` on 2026-10-04, maintainer)** (no `fraction`, no `share`); target ratios come later, once the dataset is big; deeper categories (Gate 1-A, 1-B, ...) are
hierarchical paths (`recruitment/party`), a recipe key covers everything below it and the most specific key wins; bot and spam are ordinary categories and are translated. **Recruitment walls (the >150-char, 2+ `ID:` rows that
`clean_reason` drops as "recruitment spam") are allowed into training in a small share, trusting Gate 1** — through an explicit recipe field (`"keep": ["recruitment spam"]`, default none, so no recipe = today's output),
recorded in the manifest. Watch: `cutoff_len` is 256, a wall's Korean can be cut mid-sentence by the cutoff (check `inspect_pair.py` tokens vs cutoff) — keep the share small.
- **Recipe** `configs/datasets/<name>.json`: `{description?, seed, total|null, keep: [...], categories: {path: {weight}}}`; weights are relative (no sum to 1); total = the largest dataset the weights allow (the bottleneck category is named) or `total`. **Built in G2-1 (`dataset_recipe.py`, 2026-10-04): there is no `default`** — a line no key covers is left out, and lines with no entry in the categories file are the category `uncategorized`, which can get a share like any other. Counts per key follow the weights by Sainte-Lague (line j of a key enters at (2j-1)/weight), so a longer dataset only adds lines (plain largest-remainder rounding would not); when a key runs out, the lines tied with the missing one stay out too, so the shares are exact at the end.
- **Categories file** (data, gitignored): JSONL `{key, category[, confidence, by]}`, key = sha1 of `overlap.match_key(original)` (as `valsplit.bucket`); uncategorized lines follow `default`. Any script can write it, Gate 1 later.
- **Selection** per category by rank `sha1(seed + key)` (salted: not correlated with the validation bucket); nested: a smaller `total` is a prefix of a larger one. Validation lines are decided by hash of ALL usable lines, before the recipe,
  so they are identical for every recipe (eval loss comparable across recipes); reverse rows follow their forward row.
- **Pipeline**: `preprocess.py --recipe NAME` (+ `run_pipeline.py --recipe` -> env `RESONANCE_RECIPE`, flag wins); no recipe = byte-identical output; "not selected (recipe)" is an EXPECTED reason (outside the `--max-drop` guard).
- **MLflow** (the manifest already feeds it: `tracking.dataset_tags` / `data_params` -> HF revision, train/val/raw sha256, row counts, drop reasons, prompt fingerprint; the manifest file is a run artifact): the manifest gets a `recipe` block
  (name, sha256, seed, categories-file sha256, available/selected per category); tags `dataset.recipe`, `dataset.recipe_sha256`, `data.categories_sha256`; params `data.recipe.seed` and `data.cat.<category>` (selected rows);
  `compare_runs.summarize` gets a `recipe` column. Not planned: `mlflow.data` dataset objects (they would need support in the offline queue; not checked).
- **Notebook**: preview (per category: lines, usable train-side lines, natural share, pending Korean), choose (edit a dict, see counts + bottleneck, save the recipe), `ParamSet.recipe` for sweeps over recipes.
